2026-10-05. Package `com.partner.mhyscanner`, versionCode 5 / versionName 0.1.4.

## Actual owner-session evidence

0.1.3 still failed after community confirmation. The owner reported the server explanation:

```
retcode=-1
decode err response body error: unexpected end of JSON input
SToken version=v2
```

This was text inside a successfully parsed JSON error response, not a local QR/JSON decoding exception.

A saved QR replay returned -3501 because the ticket had expired. To avoid more approvals and avoid extracting credentials into tooling, a temporary standard JVMTI debugger probe was attached **only to our own debuggable app**. It reused the approved JSONObject already held in that app's memory. It did not inspect Miyoushe or any other app. No token, full credential-bearing URL, response body, or account ID was printed/persisted by the diagnostic; only primitive results and bounded redacted descriptions were captured. No game scan/confirm was submitted.

The Passport Cookie request exposed a real frequency rejection, but this observation does **not** prove that frequency limiting caused all earlier decode errors or that changing the endpoint resolves the authorization bug. **No game_token has been obtained/saved successfully.** A successful login is not claimed, and the exact official cooldown duration is not known. All additional comparisons stopped on explicit rate limiting.

## Client changes

- Route game-token exchange to `https://passport-api.mihoyo.com/account/auth/api/getGameToken` rather than the legacy proxy.
- Keep community QR creation/query separate, using the existing Miyoushe passport app endpoints and headers.
- Recognize 1001 as frequency limiting even without a server message.
- Add a process-local monotonic 120-second minimum cooldown after frequency rejection. Repeated clicks during that period throw a local error **without sending another request**. The minimum delay does not imply official rate limiting has ended.
- Do not offer format switching for verification, signature, frequency, or upstream JSON-decoding failures. No automatic background retry.
- Keep SToken in the existing dialog's memory only; only a successfully issued game_token is intended for encrypted vault storage.

## Follow-up: 2026-10-05, after 22:03

Its dialog held another confirmed authorization and was using the explicitly selected reference-query format. ApiClient was again updated through standard RedefineClasses (return 0), without restarting the activity or reading/exporting credentials.

The new Passport route in this format therefore still reproduces the original failure. **The endpoint-migration hypothesis did not fix the bug.** No further authenticated requests, alternative-host trials, or game-login confirmations were made in this follow-up. The existing confirmation remains in the dialog's memory.

Research rechecked UIGF's token documentation and public scanner issue reports. They provide the old SToken-to-game_token route but no verified current fix for this exact failure; the related PizzaHelperUnited QR fix concerns a different, deprecated game-QR creation endpoint. It is not evidence that our already-successful community QR confirmation needs replacing.

A correct authenticated regression signal now exists (one existing UI retry, exact server error), but no authenticated green result exists. Protocol support, authorization scope, and the upstream service remain unresolved. Do not describe this as a successful game login or a proven rate-only problem. Permanent 0.1.4 installation is still postponed to preserve this confirmed dialog; `--dont-kill` is documented for adding feature splits, not a guaranteed safe full-base APK replacement.
