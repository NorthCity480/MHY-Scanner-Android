# 0.1.6 — community QR login, aligned with modern PC protocol

2026-10-05. Package `com.partner.mhyscanner`, versionCode 7 / versionName 0.1.6.

## Evidence and corrected diagnosis

The owner reports that the PC tool can add the same account and explicitly requires a **Miyoushe community login QR**, not a game SDK QR. Original repo/tag source and current release are not synchronized:

- DSVVA/MHY_Scanner v1.16.0 tagged `WindowLogin.cpp` calls a game SDK account QR with app_id=2, then GameToken→SToken. A short-lived Android 0.1.5 implementation followed that obsolete source. It passed 53 synthetic tests but did not satisfy the user's community-QR requirement. It was installed, withdrawn, and rolled back to community-based 0.1.4 without uninstall/data-clear. No successful owner authorization or game login was claimed for 0.1.5.
- The official PC v1.16.0 binary archive has SHA-256 `e631cf3caac15b934a728e85a758ee5b1f8fd779f3961fbe6ba8d0d10dd56bf4`, matching GitHub release metadata. Static literal inspection (no execution) found community create/query/scan/confirm endpoints and app ID `dw9y09jqjpxc`, but not old getGameToken/GameToken→SToken/SDK-QR-fetch literals. This is evidence of a release/source discrepancy, not a complete decompilation.
- GPL source at `loqwe/MHY_Scanner2`, pinned commit `d07fc8018414e2b54962264517d8344601d825f2`, contains the matching community endpoints and app ID, parses confirmed SToken/MID/aid directly, and uses Panda→Passport for games.

Earlier 0.1.1–0.1.4 confirmed community login but incorrectly required an additional SToken→game_token exchange to count account addition as successful. That unnecessary step returned upstream -1 and sometimes real frequency rejection. Removing it fixes this client-flow mismatch. **The server-internal cause of the old decode error remains unproved.**

## Implemented flow

1. Fixed `https://passport-api.mihoyo.com/account/ma-cn-passport/app/createQRLogin` / `queryQRLoginStatus`, community app ID `dw9y09jqjpxc`, local device UUID. No game SDK account QR creation.
2. Strict HTTPS community page validation: host/path/fragment, matching ticket, token_types=1, duplicate-parameter and optional expiry checks. Fixed credential destinations, no redirects or QR-controlled API target.
3. Confirmation selects token_type=1, validates aid/MID/SToken and official verification flags, and returns a typed community account. **No extra network call or game-token conversion happens here.**
4. The UI explicitly discloses encrypted storage of SToken/MID before confirmation. The existing Keystore AES-GCM vault now records credential kind and MID; legacy records without kind remain game_token. MainActivity saves the typed account intact, never through the legacy token-only overload.
5. For subsequently authorized game sessions, a community account uses Panda scan with passport_app_id, then a validated community ticket on fixed Passport scanQRLogin. A separate manual or session-authorized automatic action performs confirmQRLogin. Imported game_token accounts retain the old SDK flow. SToken cannot enter the legacy game-token payload.
6. The immutable scanned result is bound to its account snapshot. Cancellation between Panda and Passport prevents sending credentials; session IDs still reject stale frames/continuations. Official API rejection stops monitoring rather than background retrying. Frequency rejection retains the monotonic local minimum cooldown; it does not claim official recovery or bypass controls.
